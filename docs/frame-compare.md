# 跨端逐帧比对与时间加速

> 一条命令：同一份剧本在原版与 Web 版各跑一遍，各出 N 帧，逐帧算差异，
> 超过阈值即判为回归，并报告**第一个偏离的帧号**。
>
> 实现：`tools/compare-frames.sh`（编排）、`tools/src/devtools/ExportTrace.java`
> 的 `--frames`（原版侧出图）、`web/scripts/compare.ts`（Web 侧出图 + 报告）、
> `web/src/compare/`（判据、PNG 编解码、期望表）。剧本格式见
> `docs/trace-format.md`。

## 命令

```bash
tools/compare-frames.sh                          # 全部剧本
tools/compare-frames.sh dorm-walk                # 只跑一份
tools/compare-frames.sh --every 50               # 每 50 个 tick 取一帧（默认 25）
tools/compare-frames.sh --threshold 0.001        # 一帧里超过千分之一的像素偏了才算偏离
tools/compare-frames.sh dorm-walk --self-check   # 故意改坏一处渲染，验流水线响不响
tools/speed-probe.sh                             # 两端时间加速的实测线性度
```

需要 Java（`brew install openjdk@17`）与本机的 Chrome（`CHROME=…` 可指定路径）。
两样都不在 CI 里，所以这条流水线不在 CI 里；进 CI 的是它的**判据**
（`web/src/compare/*.test.ts`，`pnpm test`）。

产物在 `tools/traces/compare/<剧本>/`，**不入库**（`tools/.gitignore`）：

| 目录 | 内容 |
|---|---|
| `java/` | 原版真的画出来的位图（`ScenePanel.backImage`），加 `frames.json` 清单与本次导出的 trace |
| `web/` | 真浏览器里 Pixi 真的画出来的位图 |
| `web-broken/` | 只有 `--self-check` 才有：故意改坏渲染那一遍 |
| `diff/` | 差异图，洋红 = 超出容差 |
| `../report.json` | 机器可读的报告 |

## 两端是怎么跑同一份剧本的

原版侧就是 trace 导出器多存了几张图：它每个 tick 真的调一次 `paint()`
（`paint()` 有副作用，不能省），`--frames` 只是把那张已经画好的
1024×640 位图每 n 个 tick 写成 PNG，并记一份**帧清单**。

Web 侧是一个 dev-only 的取图页（`web/replay.html` + `src/replay/main.ts`），
在**真的无头 Chrome** 里跑真的 Pixi 渲染器，按 trace 里那一 tick 实际喂给原版的
按键回放（与 `src/state/traceReplay.test.ts` 同一套），推进到清单里的每个 tick
再截一张图。

三处关键决定：

- **比哪些帧只有一个来源**：清单由原版侧生成，Web 侧照着走。两端各算各的
  采样点，是错位的现成入口；而错位之后每一帧都不一样，报告只会说"全红"。
- **回放的是按键，不是坐标**。喂坐标等于把两端的分歧提前抹平：图会一直一致，
  而游戏是错的。
- **必须是真浏览器**。在 Node 里拿一个软件光栅器重画一遍，比的就是那个光栅器，
  不是被移植的渲染代码。CDP 客户端是自己写的一百来行（`web/scripts/cdp.ts`），
  Node 内建的 `WebSocket` 与 `fetch` 就够，不引 puppeteer。

## 判据：为什么不是哈希

本项目已经为这件事付过一次学费：取景器截了 4800 帧战斗，用 MD5 判"唯一帧"，
报出"60/60 唯一、没问题"，而实际上 16 场里 14 场两秒后完全静止、九成的帧是废的
——行动条挪一个像素就算"不同"，这个判据没有诊断力。

所以量的是**有多少像素差了多少**，并且把差异的**位置**一起报出来
（`web/src/compare/diff.ts`）：

| 量 | 作用 |
|---|---|
| `tolerance`（默认 8） | 单通道容差。地图资产在 Web 侧走 WebP，JPG 源那批是有损的，逐字节相等做不到也不该要求 |
| `ratio` | 超出容差的像素占比，判"这一帧算不算偏了" |
| `threshold`（默认 0.0002） | `ratio` 超过它就算偏离 |
| `maxDelta` / `box` | 坏了要长得不一样：整屏差一点点（资产编码）与一小块差很多（画错了一个精灵）必须分得出来 |

分母是**剧本条数 × 各自的帧数**，开跑前就数得出来，报告里逐条印出来。
空的帧序列、清单里有而磁盘上没有的帧、两端尺寸不同，一律硬失败——
"一帧都没比"和"比了全过"在任何只看退出码的检查里长得一模一样。


整轮（含自检那一遍取图）约 3 分钟，其中原版侧出图与 Web 侧出图各占一半。
"通过"在这里的意思是**符合期望表**，不是"两端一致"——三条现在全都差得很远，
差在哪由下一节的期望表逐条钉住。

把某条剧本的期望从 `gap` 改成 `match` 再跑，它会红成
`失败 … 回归：第 0 帧起偏离`，退出码 1（已实测）。

## 期望表：为什么"现在必然红"不等于没用

Web 版还没画 NPC、没做旁白与对话框，跨端比对现在必然红。一条恒红的检查
第二天就变成噪声；而把阈值放松到能过，就变成了这个项目最贵的那种检查——
通过条件是"没找到问题"。

`web/src/compare/expected.ts` 因此让每条剧本**显式表态**，且**两头都会红**
（`src/assets/knownMissing.ts` 是同一个套路）：

- `match` 的剧本出现偏离帧 → 红，报告指出第一个偏离的帧号；
- `gap` 的剧本一帧都不偏了 → **也红**，说明缺口补上了、这张表过期了；
- 磁盘上有而表里没表态的剧本 → 红。名单从 `tools/traces/scripts/` 现扫，
  不抄第二份。

## 自检：故意改坏一处渲染

每条剧本都红着的时候，一条恒红的流水线与一条恒绿的流水线一样没有诊断力，
而两者都能安安静静地退出 0。`--self-check` 是这件事的可执行答案：

从采样帧中间那一帧起，取图页把主角**画偏 8 像素**（世界状态一个字节不动，
坏的只有画出来的那一帧），然后断言两件事——注入点之前每一帧的差异逐帧不变，
以及差异第一次变化的帧号**正好是注入点**。

实测（2026-09-06，dorm-walk，22 帧，每 25 个 tick 取一帧）：

```
流水线自检：故意改坏一处渲染
  取图 dorm-walk：22 帧（第 275 tick 起故意改坏渲染）
  通过  dorm-walk    22 帧 · 注入点 #275 · 首个变化帧 #275 · 变了 11/22 帧
```

把注入的位移改成 0（等于"没改坏"）之后它确实会红，报的是
`首个变化帧 无（改坏了却没响）`——这条自检本身也验过它的失败态长什么样。

## 第一件被量出来的事：原版画地图是拉伸的

流水线跑起来的第一天就量到：宿舍第 0 帧两端 **83%** 的像素不同，而画面用眼睛
看完全一样。

原因在 `src/scene/Map.java`：`isStatic` 是 Java 的布尔默认值 `false`，而它唯一的
赋值（`row > 20 || col > 32`）也是赋 `false`，所以

```java
g.drawImage(image, 0, 0, 32 * 32, 20 * 32,
            firstTileX * 8, firstTileY * 8, lastTileX * 8 - 8, lastTileY * 8 - 8, scene);
```

这条**拉伸**分支恒成立，`g.drawImage(image, 0, 0, scene)` 那条 1:1 分支是死代码。
宿舍的视口是 `firstTile(0,0)` / `lastTile(128,80)`，源矩形因此是 `(0,0)-(1016,632)`，
被拉到 1024×640，放大 1.0079 倍。实测 x=1000 处两端错开 8 像素、x=10 处错开 0，
正是这个比例。

Web 侧现在把地图 1:1 贴上去，于是整屏都差一点点。这不是"资产不一致"——
`maps/宿舍.png` 与烘出来的 `宿舍.webp` **解码后逐像素相同**（无损 WebP，已实测：
浏览器把 WebP 贴成 `<img>` 截下来，与源 PNG 的 655360 个像素一个不差），
差的是画法。跟票：`xl-9bd.16`。

**不要去"修好"原版**——迁移期间原版是规格。

## 时间加速

两端都能按倍率加速，且**加速不改变游戏行为**：

- Java 侧是 `tools.Clock`，把散在 16 个文件的 30 处时间常数收拢成一个可缩放量；
- Web 侧是 `state/loop.ts` 的 `Ticker.timeScale`，倍率乘在**真实流逝的毫秒**上。
  这一侧不需要收拢时间常数，因为时间本来就是 `step()` 的入参。

Web 侧的倍率**不乘在 tick 步长上**。那是最顺手的写法，但会跳过定时器的触发
时刻，主角走的距离立刻对不上真值。判据写成了一条不变量：**k× 跑 T 毫秒，
与 1× 跑 k·T 毫秒得到逐字段相同的世界**（`src/state/loop.test.ts`，四个倍率）。

墙钟实测（`tools/speed-probe.sh`，2026-09-06，macOS / openjdk 17 / Node 24）：

```
Java 侧（tools.Clock.sleep，每个倍率量 2000 游戏毫秒）
  factor=1.0   真实  2306.3 ms  绝对倍率  0.87×  相对首行  1.00×
  factor=2.0   真实  1306.1 ms  绝对倍率  1.53×  相对首行  1.77×
  factor=5.0   真实   525.0 ms  绝对倍率  3.81×  相对首行  4.39×
  factor=10.0  真实   265.4 ms  绝对倍率  7.54×  相对首行  8.69×

Web 侧（state/loop.ts 的推进器，每个倍率量 400 真实毫秒）
  scale=1     真实   403.9 ms  游戏    400 ms  实测倍率  0.99×  偏差 1.0%
  scale=2     真实   403.6 ms  游戏    800 ms  实测倍率  1.98×  偏差 0.9%
  scale=5     真实   402.6 ms  游戏   2010 ms  实测倍率  4.99×  偏差 0.2%
  scale=10    真实   404.2 ms  游戏   4040 ms  实测倍率  9.99×  偏差 0.1%
```

Java 侧的**绝对**倍率被 `Thread.sleep` 的固定超时开销压低（每次多睡几毫秒，
与倍率无关），所以那一列恒小于 1；回答"线不线性"的是**相对首行**那一列。
它与 `docs/MIGRATION-PLAN.md` §4 里那张战斗层面的表（1.00 / 1.86 / 3.84 / 7.41）
同一个量级。Web 侧偏差最大 1.0%，探针在超过 20% 时非零退出——加速封顶的
表现是游戏"跑得没那么快"，不报错，所以必须有人量。

**跨机器、跨 JDK / Chrome 版本的一致性未验证。** 上面每个数字都是这一台机器
上的一次实测。

## 加一条机制剧本要做什么

1. 往 `tools/traces/scripts/` 里写剧本（格式见 `docs/trace-format.md`）；
2. `tools/export-trace.sh --check` 导出并验确定性，产物入库；
3. 在 `web/src/compare/expected.ts` 里表态：现在该 `match` 还是 `gap`
   （`gap` 要写清楚差在哪、挂哪张票）。漏了这一步 `pnpm test` 就红。
