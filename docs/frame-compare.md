# 跨端逐帧比对与时间加速

> 一条命令：同一份剧本在原版与 Web 版各跑一遍，各出 N 帧，逐帧算差异，
> 超过阈值即判为回归，并报告**第一个偏离的帧号**。
>
> 实现：`tools/compare-frames.sh`（编排）、`tools/src/devtools/ExportTrace.java`
> 的 `--frames`（原版侧出图）、`web/scripts/compare.ts`（Web 侧出图 + 报告）、
> `web/src/compare/`（判据、PNG 编解码、期望表）。剧本格式见
> `docs/trace-format.md`。

## 命令

```bash
tools/compare-frames.sh                          # 全部剧本
tools/compare-frames.sh dorm-walk                # 只跑一份
tools/compare-frames.sh --every 50               # 每 50 个 tick 取一帧（默认 25）
tools/compare-frames.sh --threshold 0.001        # 一帧里超过千分之一的像素偏了才算偏离
tools/compare-frames.sh dorm-walk --self-check   # 故意改坏一处渲染，验流水线响不响
tools/speed-probe.sh                             # 两端时间加速的实测线性度
```

需要 Java（`brew install openjdk@17`）与本机的 Chrome（`CHROME=…` 可指定路径）。
两样都不在 CI 里，所以这条流水线不在 CI 里；进 CI 的是它的**判据**
（`web/src/compare/*.test.ts`，`pnpm test`）。

产物在 `tools/traces/compare/<剧本>/`，**不入库**（`tools/.gitignore`）：

| 目录 | 内容 |
|---|---|
| `java/` | 原版真的画出来的位图（`ScenePanel.backImage`），加 `frames.json` 清单与本次导出的 trace |
| `web/` | 真浏览器里 Pixi 真的画出来的位图 |
| `web-broken/` | 只有 `--self-check` 才有：故意改坏渲染那一遍 |
| `diff/` | 差异图，洋红 = 超出容差 |
| `../report.json` | 机器可读的报告 |

## 两端是怎么跑同一份剧本的

原版侧就是 trace 导出器多存了几张图：它每个 tick 真的调一次 `paint()`
（`paint()` 有副作用，不能省），`--frames` 只是把那张已经画好的
1024×640 位图每 n 个 tick 写成 PNG，并记一份**帧清单**。

Web 侧是一个 dev-only 的取图页（`web/replay.html` + `src/replay/main.ts`），
在**真的无头 Chrome** 里跑真的 Pixi 渲染器，按 trace 里那一 tick 实际喂给原版的
按键回放（与 `src/state/traceReplay.test.ts` 同一套），推进到清单里的每个 tick
再截一张图。

三处关键决定：

- **比哪些帧只有一个来源**：清单由原版侧生成，Web 侧照着走。两端各算各的
  采样点，是错位的现成入口；而错位之后每一帧都不一样，报告只会说"全红"。
- **回放的是按键，不是坐标**。喂坐标等于把两端的分歧提前抹平：图会一直一致，
  而游戏是错的。
- **必须是真浏览器**。在 Node 里拿一个软件光栅器重画一遍，比的就是那个光栅器，
  不是被移植的渲染代码。CDP 客户端是自己写的一百来行（`web/scripts/cdp.ts`），
  Node 内建的 `WebSocket` 与 `fetch` 就够，不引 puppeteer。

## 判据：为什么不是哈希

本项目已经为这件事付过一次学费：取景器截了 4800 帧战斗，用 MD5 判"唯一帧"，
报出"60/60 唯一、没问题"，而实际上 16 场里 14 场两秒后完全静止、九成的帧是废的
——行动条挪一个像素就算"不同"，这个判据没有诊断力。

所以量的是**有多少像素差了多少**，并且把差异的**位置**一起报出来
（`web/src/compare/diff.ts`）：

| 量 | 作用 |
|---|---|
| `tolerance`（默认 8） | 单通道容差。地图资产在 Web 侧走 WebP，JPG 源那批是有损的，逐字节相等做不到也不该要求 |
| `ratio` | 超出容差的像素占比，判"这一帧算不算偏了" |
| `threshold`（默认 0.0002） | `ratio` 超过它就算偏离 |
| `maxDelta` / `box` | 坏了要长得不一样：整屏差一点点（资产编码）与一小块差很多（画错了一个精灵）必须分得出来 |

分母是**剧本条数 × 各自的帧数**，开跑前就数得出来，报告里逐条印出来。
空的帧序列、清单里有而磁盘上没有的帧、两端尺寸不同，一律硬失败——
"一帧都没比"和"比了全过"在任何只看退出码的检查里长得一模一样。

整轮（含自检那一遍取图）约 3 分钟，其中原版侧出图与 Web 侧出图各占一半。
"通过"在这里的意思是**符合期望表**，不是"两端一致"——三条现在全都差得很远，
差在哪由下一节的期望表逐条钉住。

把某条剧本的期望从 `gap` 改成 `match` 再跑，它会红成
`失败 … 回归：第 0 帧起偏离`，退出码 1（已实测）。

## 期望表：为什么"现在必然红"不等于没用

Web 版还没画 NPC、没做旁白与对话框，跨端比对现在必然红。一条恒红的检查
第二天就变成噪声；而把阈值放松到能过，就变成了这个项目最贵的那种检查——
通过条件是"没找到问题"。

`web/src/compare/expected.ts` 因此让每条剧本**显式表态**，且**两头都会红**
（`src/assets/knownMissing.ts` 是同一个套路）：

- `match` 的剧本出现偏离帧 → 红，报告指出第一个偏离的帧号；
- `gap` 的剧本一帧都不偏了 → **也红**，说明缺口补上了、这张表过期了；
- `gap` 的剧本偏得比声明的多 → **也红**（下一节）；
- 磁盘上有而表里没表态的剧本 → 红。名单从 `tools/traces/scripts/` 现扫，
  不抄第二份。

## 幅度上界：偏多少也算数

上面那两条只管"有没有偏离"，不管偏了多少——而**灾难性的错误同样能提供偏离**。
实测（2026-09-06，xl-l3o）：把基准侧 `ExportTrace.dumpFrame` 里那张位图换成
全黑的 1024×640，`dorm-walk` 的最差帧从 0.7401% 跳到 99.9565%，流水线退出 0、
报"1/1 条剧本符合预期"。这正是本仓库那句"失败的样子和成功一模一样"。

所以每笔账都有上界（判据在 `web/src/compare/verdict.ts` 与 `regions.ts`）：

- 整屏表态写 `maxRatio`——**每一帧**的差异占比都必须 ≤ 它；
- 分区表态给每个缺口区写 `maxPixels`——**每一帧**里那个区超容差的像素数上限。

上界是**每帧**而不是所有帧之和：采样密度由 `--every` 定，帧数一变和值跟着变，
一张按 `--every 25` 量出来的和值表换个采样就是错的，而且是往松了错。单帧的量
与采样密度无关——多采几帧只可能采到更差的帧。

**取值一律实测，余量一律 2 倍。** 上界要挡住"什么都没画出来"，又不能让另一台
机器的正常抖动变红。这条流水线上最会抖的是**后备字体**：本仓库记录的实测
（xl-9bd.17 / xl-9bd.18）里，`dorm-intro` 最会写字的那一帧 t=800 在
5.5397% → 5.6325% → 2.8482% 之间来回，最宽一档 1.98 倍；这一次重量到的正是
2.8482%。2 倍盖得住"这台机器挑了另一条后备链"，盖不住"这一帧没画出来"
（全黑 ≈ 100%）。重编码那几条（两端解码器都定死）其实稳得多，2 倍对它们是宽的
——宁可规则统一、余量说得清，也不要每条剧本各拍一个数。

这一次量到的五条（`--every 25`，容差 8，共 636 帧）与它们的上界：

| 剧本 | 最差帧 | 上界 | 篡改成全黑之后 |
|---|---|---|---|
| bigmap-walk | #475 37.1101% | 74.22% | #0 99.9751%（1.35 倍） |
| dorm-exit | #875 34.0767% | 68.15% | #525 99.9867%（1.47 倍） |
| dorm-intro | #800 2.8482% | 5.70% | #3725 99.9649%（17.54 倍） |
| milestone | #8825 29.1754% | 58.35% | #8800 99.9921%（1.71 倍） |
| dorm-walk（分区） | coin-hud 527 / speech-name 1397 / speech-text 4323 | 1054 / 2794 / 8646 | 1104、11152、92833，三个区**全部**超界，硬比区同时破 |

全黑那一轮 `tools/compare-frames.sh`（不带剧本名，五条全跑）退出码 1，报
"5/5 条剧本不符合预期"，并逐条点名超了多少倍。

**另一头没被挤掉。** 同一天的第二次篡改：把 `dorm-intro` 与 `dorm-walk` 的 Web
侧 187 张帧直接抄成基准侧的（差异归零，等于"缺口全补上了"），退出码仍是 1 ——
整屏那条报"缺口没了…把 expected.ts 里这条改成 match"，分区那条报"缺口区
coin-hud、speech-name、speech-text、hero-run 一帧都不差了"。上界与下界各管一头。
（那一轮里 `hero-run` 还在表上；它已经在 xl-u39 里还掉了，见下面那一节。）

上界还必须**够得着**：`expected.test.ts` 里有一条检查，缺口区的 `maxPixels`
不许大于这块区自己的面积——破不了的检查和没有检查是同一件事，而两者都安安静静
地通过。`coin-hud` 那一格就是这条检查的现实意义：它的区里一共 1104 个像素，
上界 1054，全黑时刚好超 50 个。

## 分区表态：硬比区逐像素，缺口区各自记账

整屏一个状态的表态只说得出"这条剧本红着"，红在**哪儿**由注释里的一段散文钉住
——而散文不会在缺口挪了位置的时候变红。缺口挪到别处、或者多长出一块新的偏离，
`status: gap` 照样通过。

`Expectation` 因此有一个可选的 `gaps`（xl-1vu.3），判据在
`web/src/compare/regions.ts`：

- 声明出来的矩形是**缺口区**，照旧记账；
- 矩形**之外**全是**硬比区**，每一个像素都必须在容差内相等。不是"超过阈值才
  算偏"，是**一个都不许有**；
- **每个缺口区各自双向红**：某个区一帧都不差了就红。整屏版的双向红只有一个
  分母，三个缺口里补上一个根本看不出来。

写了 `gaps` 的剧本走这一套，没写的照旧。表那一层还有三条约束
（`expected.test.ts`）：区之间**不许重叠**（重叠会让"这个区归零了"不再可判）、
每个区要写 `why` 与 `xl-` 票号、**所有区加起来不许超过画布的 40%**——"把区画大
一点让它过"是这套判据唯一的作弊路子。

### dorm-walk：第一条分区表态

实测（`tools/compare-frames.sh dorm-walk --every 25`，22 帧，容差 8）：

```
  通过  dorm-walk      22 帧 · 首个偏离帧 #0 · 偏离 22/22 · 最差 #500 0.7401%
        硬比区 22 帧逐像素相等；coin-hud 合计 11594、最差 527/1054 ·
        speech-name 合计 1397、最差 1397/2794 · speech-text 合计 9009、
        最差 4323/8646
```

（`最差 527/1054` 是"这个区最差的一帧差了 527 个像素，上界 1054"，见上一节。）

11594 = 527 × 22，正是右下角那块还没画的金币 HUD。也就是说：地图、家具、NPC、
主角的走动帧**与跑动帧**、对话框的边框与名字牌本身，在这条剧本的每一帧上都逐
像素相等——这句话以前只能靠读注释相信。（跑动帧原先是个例外，见下一节。）

### 分区量出来的那一笔账，以及它是怎么还掉的（xl-u39）

分区判据立起来的当天顺手量出了一笔没人记过的账：`hero-run`。`runTo` 那一段的
三帧（t=225/250/275）在 HUD 之外各差 412/360/368 个像素，包围盒都落在跑步精灵
那 42×64 的框里，而**走动**的帧在 HUD 之外差 0 个。整体平移 dx∈[-3,3]、
dy∈[-1,1] 再比，(0,0) 是唯一最优（412 对次优 5114），所以不是错位，是内容不同。

**结论不是它猜的那个。** 票上怀疑跑步帧号（`Role.count2` / web 的 `runFrame`）
两端推进不一致，而 `count2` 当时不在真值里。把它补进 scene 真值之后逐 tick 比对
全绿——两端的推进**一模一样**，起点与步长都不差。真正的原因在素材尺寸：

`roles/zhangxiaofanRun/15.png` 与 `16.png` 是 42×65，其余 14 张 42×64。原版
`Role.drawHero` 的 `drawImage` 带**源矩形** `(0,0)-(42,64)`，多出来的那一行是被
**裁**掉的；而 Web 侧 `sceneRenderer` 走 `setSize(42, 64)`，那是**缩**——65 行
重采样成 64 行。这两张正好是朝右的第 3、4 帧，也正是那三帧画到的。烘焙器改成
按源矩形裁之后，这三帧归零。

**这笔账是被判据自己催着还的**：修好之后 `expected.ts` 还没改，跑一次比对就得到

```
  失败  dorm-walk      22 帧 · …
        缺口区 hero-run 一帧都不差了 —— 账还完了而表没改，把这些区从
        expected.ts 的 gaps 里删掉（删干净之后整条就该是 match）。
```

也就是下面那张篡改表里第三行同一条路径，只是这一次不是篡改，是真的补上了。

## 装配不出来的驱动器：未实现的 web 侧必须响亮（xl-1vu.7）

四种驱动器的真值现在都齐了（场景 / 战斗 / 菜单 / 商店，见 `docs/trace-format.md`
的「四种驱动器一览」），而**取图页只装配得出 `scene`**。剩下三种在这条流水线里
必须响亮地失败：一条没被装配的剧本比出来是「零帧差异」，跟「两端完全一致」长得
一模一样。

流水线因此**在开浏览器之前先分流**。分流的两份记录互不抄袭：

| 记录 | 说的是 | 在哪 |
|---|---|---|
| 名单 | 取图页**能**装配哪些判别名 | `web/src/replay/implemented.ts` |
| 表态 | 每条剧本**声称**自己现在什么处境 | `web/src/compare/expected.ts` 的 `status` |

`web/src/compare/unassembled.ts` 拿这两份对撞，**两个方向都是硬失败**：表说
`match`/`gap` 而页面装不出（那笔账是编的，一帧都没比过）；页面已经装得出而表
还写 `unassembled`（面板做好了而表没改，这条剧本会永远挂在"比不了"上）。
判据在 `web/src/compare/unassembled.test.ts`，跑在 `pnpm test` 里 —— 不需要 Java
与 Chrome，所以它进 CI，而整条流水线不进。

名单为什么不能抄两份：`web/src/replay/main.ts` 的装配表声明成
`Record<ImplementedDriver, Assembly>`，**少一个键或多一个键都是编译错** ——
这道是常开的，`pnpm typecheck` 每次都过。跑起来之后页面还把
`Object.keys(ASSEMBLIES)` 挂在 `window.__xlDrivers` 上，比对器进门核一次
（`assertPageAgrees`），核不上是硬失败，不许降级成"那就信本地这份"；不过**这第二道
只在这一轮真的要取图时才跑** —— 一轮里全是装配不出来的剧本时压根不开浏览器
（`tools/compare-frames.sh menu-equip` 就是这种），那一轮守着的只有类型那道。

**为什么要提前分流而不是撞上去。** 从前是撞上去的：取图页对未实现的驱动器抛，
异常转成 Node 侧的 Error，整轮**中断**。于是默认全跑时 —— 按字典序第一条正好是
`battle-em3-box` —— 五条能比的场景剧本一帧都比不成，`--self-check` 也跟着不跑。
一条把自己噎死的流水线与一条恒绿的流水线，实用价值是一样的。

实测（2026-09-06，`tools/compare-frames.sh --self-check`，9 条剧本，退出码 **1**）：

（逐字照抄，只删掉五条剧本各自的第二行判词与取图进度行；其余一字未改）

```
跨端逐帧比对：5 条剧本 × 各自的帧数 = 636 帧（阈值 0.0200% 的像素，单通道容差 8）
```

## 自检：故意改坏一处渲染

每条剧本都红着的时候，一条恒红的流水线与一条恒绿的流水线一样没有诊断力，
而两者都能安安静静地退出 0。`--self-check` 是这件事的可执行答案：

从采样帧中间那一帧起，取图页把主角**画偏 8 像素**（世界状态一个字节不动，
坏的只有画出来的那一帧），然后断言两件事——注入点之前每一帧的差异逐帧不变，
以及差异第一次变化的帧号**正好是注入点**。

实测（2026-09-06，dorm-walk，22 帧，每 25 个 tick 取一帧）：

```
流水线自检：故意改坏一处渲染
  取图 dorm-walk：22 帧（第 275 tick 起故意改坏渲染）
  通过  dorm-walk    22 帧 · 注入点 #275 · 首个变化帧 #275 · 变了 11/22 帧
```

把注入的位移改成 0（等于"没改坏"）之后它确实会红，报的是
`首个变化帧 无（改坏了却没响）`——这条自检本身也验过它的失败态长什么样。

## 第一件被量出来的事：原版画地图是拉伸的

流水线跑起来的第一天就量到：宿舍第 0 帧两端 **83%** 的像素不同，而画面用眼睛
看完全一样。

原因在 `src/scene/Map.java`：`isStatic` 是 Java 的布尔默认值 `false`，而它唯一的
赋值（`row > 20 || col > 32`）也是赋 `false`，所以

```java
g.drawImage(image, 0, 0, 32 * 32, 20 * 32,
            firstTileX * 8, firstTileY * 8, lastTileX * 8 - 8, lastTileY * 8 - 8, scene);
```

这条**拉伸**分支恒成立，`g.drawImage(image, 0, 0, scene)` 那条 1:1 分支是死代码。
宿舍的视口是 `firstTile(0,0)` / `lastTile(128,80)`，源矩形因此是 `(0,0)-(1016,632)`，
被拉到 1024×640，放大 1.0079 倍。实测 x=1000 处两端错开 8 像素、x=10 处错开 0，
正是这个比例。

Web 侧现在把地图 1:1 贴上去，于是整屏都差一点点。这不是"资产不一致"——
`maps/宿舍.png` 与烘出来的 `宿舍.webp` **解码后逐像素相同**（无损 WebP，已实测：
浏览器把 WebP 贴成 `<img>` 截下来，与源 PNG 的 655360 个像素一个不差），
差的是画法。跟票：`xl-9bd.16`。

**不要去"修好"原版**——迁移期间原版是规格。

## 时间加速

两端都能按倍率加速，且**加速不改变游戏行为**：

- Java 侧是 `tools.Clock`，把散在 16 个文件的 30 处时间常数收拢成一个可缩放量；
- Web 侧是 `state/loop.ts` 的 `Ticker.timeScale`，倍率乘在**真实流逝的毫秒**上。
  这一侧不需要收拢时间常数，因为时间本来就是 `step()` 的入参。

Web 侧的倍率**不乘在 tick 步长上**。那是最顺手的写法，但会跳过定时器的触发
时刻，主角走的距离立刻对不上真值。判据写成了一条不变量：**k× 跑 T 毫秒，
与 1× 跑 k·T 毫秒得到逐字段相同的世界**（`src/state/loop.test.ts`，四个倍率）。

墙钟实测（`tools/speed-probe.sh`，2026-09-06，macOS / openjdk 17 / Node 24）：

```
Java 侧（tools.Clock.sleep，每个倍率量 2000 游戏毫秒）
  factor=1.0   真实  2306.3 ms  绝对倍率  0.87×  相对首行  1.00×
  factor=2.0   真实  1306.1 ms  绝对倍率  1.53×  相对首行  1.77×
  factor=5.0   真实   525.0 ms  绝对倍率  3.81×  相对首行  4.39×
  factor=10.0  真实   265.4 ms  绝对倍率  7.54×  相对首行  8.69×

Web 侧（state/loop.ts 的推进器，每个倍率量 400 真实毫秒）
  scale=1     真实   403.9 ms  游戏    400 ms  实测倍率  0.99×  偏差 1.0%
  scale=2     真实   403.6 ms  游戏    800 ms  实测倍率  1.98×  偏差 0.9%
  scale=5     真实   402.6 ms  游戏   2010 ms  实测倍率  4.99×  偏差 0.2%
  scale=10    真实   404.2 ms  游戏   4040 ms  实测倍率  9.99×  偏差 0.1%
```

Java 侧的**绝对**倍率被 `Thread.sleep` 的固定超时开销压低（每次多睡几毫秒，
与倍率无关），所以那一列恒小于 1；回答"线不线性"的是**相对首行**那一列。
它与 `docs/MIGRATION-PLAN.md` §4 里那张战斗层面的表（1.00 / 1.86 / 3.84 / 7.41）
同一个量级。Web 侧偏差最大 1.0%，探针在超过 20% 时非零退出——加速封顶的
表现是游戏"跑得没那么快"，不报错，所以必须有人量。

**跨机器、跨 JDK / Chrome 版本的一致性未验证。** 上面每个数字都是这一台机器
上的一次实测。

## 加一条机制剧本要做什么

1. 往 `tools/traces/scripts/` 里写剧本（格式见 `docs/trace-format.md`）；
2. `tools/export-trace.sh --check` 导出并验确定性，产物入库；
3. 在 `web/src/compare/expected.ts` 里表态：现在该 `match` 还是 `gap`
   （`gap` 要写清楚差在哪、挂哪张票，并**跑一遍读出最差帧、按 2 倍写上界**）。
   漏了这一步 `pnpm test` 就红。
   缺口能圈成几块矩形的，就顺手写成**分区表态**（上面那一节）——剩下那大半张
   画布因此变成硬判据，而不是继续躺在一句"已知缺口"底下。
