# 用例超时是一条全局政策，定得够宽，并且由运行时判据守着

`web/vite.config.ts` 的 `test:` 段把 `testTimeout` 设成 **30000ms**，而不是
留着 vitest 默认的 5000ms，也不是给撞上去的那一条 `it` 单独传第三参数。

理由不是「那条用例慢」，是**因为慢而红，和因为算错而红长得一模一样**。这个
仓库的验收方式是篡改验证——读的是「这次篡改让几条判据变红」。一条与篡改无关
的超时红会让人高估影响面；下一次它恰好没超时，又会让人低估。判据本身失去
分辨力，比慢得多严重。（起因：`xl-9c7`，撞上的是
`web/src/scene/viewport.test.ts` 的「夹住的帧地图被切成多块」，在 `xl-rh9.12`
的篡改矩阵里真红过两次。）

30000 是量出来的：实测最慢那条用例空闲时 696ms、全量并跑 1276ms、机器忙时
5266 / 6051ms（评审复核时在另一台负载下还读到过 3382ms）。30000 是最慢那条的
23 倍、最坏观测的 5 倍。**定这么宽是故意的**：超时该拦的是真的挂住（死循环、
永不 resolve 的 promise），那种情况多等 25 秒不花什么钱；「机器忙」不该由它
来表态。

## Considered Options

- **给撞上去的那一条 `it` 传第三参数。** 票里列的另一条修法。撞上 5000ms 的
  不会只有这一条——全量并跑时最慢的一条已经是 1276ms，离默认值只有 4 倍余量，
  而实测的负载因子有 8.7 倍。逐条打补丁等于等着下一条再撞，而且每次都要先
  经历一次「以为是判据红了」。
- **把那条慢用例改快。** 它慢是因为真的在逐 tick 扫真值，砍掉的是分辨力。
- **只在注释里写「别让用例超过 N 秒」。** 靠人记，正是这个项目反复吃亏的形状；
  而且忘了和记着长得一样。

`hookTimeout` 保持默认的 10000，**不是漏了**：全套里只有一个钩子
（`checkAssets.test.ts` 的 `afterAll`，一句 `rmSync`），没有任何实测支持动它。

## Consequences

`web/src/test/testTimeout.test.ts` 守着这条政策，两点是刻意的：

- **它读运行时生效的值**（`ctx.task.timeout`，vitest 算完各级默认与覆盖之后
  真正交给这条用例的那个数），不读 `vite.config.ts` 的字面量。配置那一行删掉，
  它立刻读到 5000 并报出来。
- **下限 30000 在判据里是手写的，故意不从配置 import。** 共用一个常量的话，
  把它改小会让配置和判据一起降下去、测试照样全绿——那是
  `docs/agents/dispatch.md` 纪律 3 记的「造出一个恒真判据」。配置那一行是
  **设置**，判据里那个数是**签下的政策**。两个数各写一处，才叫对撞。

代价：一条真的挂住的用例现在要等 30 秒才报，而不是 5 秒。这是明知的取舍——
挂住是罕见事故，误红是每次并行验收都可能发生的事。

还有一个这条政策**盖不住**的口子：给某条 `it` 单独传一个更小的第三参数，全局
判据看不见（它读的是那一条自己的生效值）。今天全仓库没有这种写法，将来有了
要单独议。
