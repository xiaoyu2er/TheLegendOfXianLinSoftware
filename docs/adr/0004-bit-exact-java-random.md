# 位精确复刻 java.util.Random

战斗里到处是随机：伤害是 `基础 - 防御 + (int)(Math.random()*15)`，敌人选招是
`(int)(Math.random()*技能数)+1`，选目标是一个会消耗不定次数随机数的拒绝采样
循环。行为真值靠反射给 `java.lang.Math` 私有的那个 `Random` 播种来保证确定性，
也就是说 Java 侧用的就是标准 `java.util.Random`——规范里写死的 48 位 LCG。

**web 端手写一份位精确的同款**，不用 `Math.random()`。不只是数值要一致，
**每次取随机数的调用顺序也要逐字一致**，多消耗一次整条序列就错位。

## Considered Options

**不复刻，比对时把伤害数字排除在外**。否掉的理由：`trace-format.md` 明写
`hurts[]` 是「这一击打了多少唯一的可断言出处」，挖掉它等于战斗最核心的一层
没有判据。

## Consequences

它是一张独立的前置票，因为判据完全自足：拿 Java 生成「种子 → 前 N 个
`nextDouble()`」的黄金数据，逐个对，不需要战斗面板存在。它一旦错，下游每一个
数字都错，那时分不清是随机数错了还是战斗逻辑错了。

JS 没有 64 位整数运算，实现上要用 `BigInt` 或把 48 位拆成两半。
