# 仙林软件奇侠传 · Java Swing → Web React 迁移计划

> 本文档记录**决策及其依据**。任务追踪在 beads（`bd list` / `bd ready`），
> 不在这里重复。文中每个数字都标注了测量方式；没有标注的是推断，不要当测量用。

---

## 0. 一句话

把 2012 年的 Java Swing RPG（87 文件 / 18,253 行 / 96 个场景脚本 / 453MB 素材）
迁移为 Pixi + React 的 Web 游戏，**玩法等价、表现层现代化**，用 beads 管理，
用**跨端剧本逐帧比对**做验收。

## 1. 已确定的决策

| # | 决策 | 依据 |
|---|---|---|
| 忠诚度 | **玩法等价重制**，尽可能贴近原版，允许优化 | 1:1 复刻的成本大头是复现无文档的手搓动画时序 |
| 版权 | 素材来自《天之痕》《仙剑》，公开部署并接受风险 | 用户决策。资产层做成可替换抽象，将来换素材不动逻辑 |
| 仓库 | 原地改造，`web/` 目录，**Java 代码保留** | Java 源码是整个迁移期唯一的规格文档，删掉它等于删掉规格 |
| 渲染 | **Pixi.js 画场景与战斗，React 画 UI**（菜单/商店/装备/技能/对话框） | 原版把 UI 画进 canvas 是 2012 年 Swing 组件太丑的历史包袱；这五块占约 1/4 代码量 |
| 数据 | **构建期烘焙** GBK → JSON，转换脚本长期保留 | 静默解析错误必须在 CI 里发生，不是在用户浏览器里 |
| 分辨率 | 锁死 **1024×640**，等比缩放 letterbox，默认平滑 + 像素锐利开关 | 实测 `getContentPane().getSize()`；战斗站位与视野范围均按此调过 |
| 存档 | IndexedDB + 新 JSON 格式，**带版本号**，不兼容旧存档 | 旧存档只有 3 个本地 txt，兼容收益约等于零 |
| 工具链 | Vite + React + **TypeScript** + pnpm，Cloudflare Pages | TS 是刚需：脚本解析结果的类型就是规格在新世界的投影 |
| 切片 | **纵向按可玩链路**，M1 = 宿舍 → 大地图 | 见 §3 |
| 架构 | **状态机与渲染彻底解耦**，由外部 tick 驱动，带 timeScale | 见 §4，这是唯一没有妥协余地的一条 |
| 验收 | **跨端剧本 + 逐帧比对** | 见 §5 |
| beads | epic = 里程碑，feature = 系统切片，bug = 缺陷 | 纯按系统拆会让 `bd ready` 里堆满不产生可玩成果的任务 |

## 4. 架构：状态机必须与渲染解耦

状态推进由外部按固定步长驱动，渲染只读世界状态、永不写它。理由不是
「原版的战斗被渲染驱动、必须解开」——**那条理由是错的，见下**——而是：用
`requestAnimationFrame` 驱动逻辑，用户切到别的标签页时浏览器把回调停掉，
战斗冻住，切回来一瞬间补跑几百帧。这是浏览器自己带来的问题，与原版长什么样
无关。战斗的固定步长决定见 `docs/adr/0003-battle-clock-is-fixed-step.md`。

> ### ⚠️ 这一节曾经写着一条错的理由
>
> 2026-09-06 之前，这里写的是「原版的 `paint()` **有副作用** —— 战斗状态机
> 是被渲染驱动的」，并引了一组控制变量读数：
>
> ```
> 不调 paint()  → command.isDraw 出现   0 / 120 帧
> 调   paint()  → command.isDraw 出现  59 / 120 帧
> ```
>
> **实测推翻（2026-09-06，openjdk 17）：战斗面板的 `paint()` 对状态机没有
> 副作用。** 同一场战斗跑两遍，一遍每步 `paint()`、一遍一次都不 `paint()`，
> 426 步 × 24 个可断言字段的逐步转储**零行差异**，两遍的胜负、步数、末帧血量
> 也都相同。所有 `update()` 都在 `BattlePanel.run()` 的循环体里，各个
> `drawXxx()` 只画不改。
>
> 上面那组读数错在**测法**，不在算术：那次测量里 `run()` 线程是自由奔跑的，
> `paint()` 只是让取样循环变慢，于是取到了更靠后的状态。它量到的是采样频率，
> 不是因果。要复现因果关系，得像 `tools/src/devtools/BattleDriver.java` 那样
> 先把闸门装在 `repaint()` 上、一步一步地推。
>
> **为什么把它留在这里而不是删掉。** 这条断言 2026-09-05 写进这份计划
> （commit `56fe5a9`），2026-09-06 被实测推翻，2026-09-07 才订正——中间它被
> 引用、被当成架构理由用，却从来没有机会失败，因为凡是照它做的人都得到了
> 一个能用的结果
> （解耦本身是对的）。删掉它，下一个人打开原版战斗代码、看到状态机和 `paint()`
> 都在一个 `JPanel` 里，很可能重新得出同一个结论，并且同样没有办法发现自己错了。
>
> **不要把这条推翻套到场景面板上。** `ScenePanel.paint()` 确实有副作用：
> 它调 `otherEvent.calOffset()` 算视口，`Dialogue.drawDialogue()` 遇到对话正文
> 里的 `@` / `$` 会写 `dialogueEvent.dialogueFight` / `gameOver`（`Dialogue.java`
> 那两个 `continue` 分支）。导出器因此每 tick 真的调一次 `paint()`，不省。
> 场景侧「不画到底会不会推进」没有做过战斗那样的控制变量实测。
> 正确结论的全文在 `docs/trace-format.md` §`paint()` 到底有没有副作用。

Web 版若照抄 rAF 驱动，会以更难查的形式复现：用户切到别的标签页，浏览器暂停
`requestAnimationFrame`，战斗冻住；切回来一瞬间补跑几百帧。

解耦后的三个收益：
1. 战斗逻辑可在**无渲染**下单元测试（给定初始状态 + N 次 tick → 断言结果）
2. `timeScale` 是免费的（tick 步长乘系数）
3. 与 Java 侧的 `tools.Clock` 一一对应，两端加速能力对称

Java 侧的 `tools.Clock` 已落地，把散在 16 个文件的 30 处时间常数
（13 个 `Thread.sleep` + 17 个 `Timer`）收拢成一个可缩放量。线性度实测：

| factor | 行动条填满耗时（两次） | 相对 1× |
|---:|---|---:|
| 1 | 15101 / 15234 ms | 1.00× |
| 2 | 8167 / 8095 ms | 1.86× |
| 5 | 4011 / 3861 ms | 3.84× |
| 10 | 2017 / 2073 ms | 7.41× |

`factor = 1.0` 时所有方法恒等，行为与原版一致（96 个真值 JSON 重新导出后逐字节无变化）。

## 5. 验收：跨端剧本 + 逐帧比对

**人眼比对不可靠，这一点在本项目里已被反复证实。**

制定计划的过程中，取景器产出的战斗截图被判定为"60/60 唯一帧、没问题"，
而实际上 16 场里 14 场在 2 秒后就完全静止、90% 的帧是废的。
用 MD5 判"唯一帧"没有诊断力 —— 行动条挪一个像素就算不同。
换成"静止起点 + 静止后最大差异"才量出真相。

所以验收必须是：

```
一份声明式剧本（"走到 (14,19)" 而不是 "按 12 次下键"）
   → Java 取景器跑一遍，出 N 帧
   → Web 版跑一遍，出 N 帧
   → 逐帧算差异，超阈值即回归，报告首个偏离帧号
```

分母固定且可数：**剧本条数 × 帧数**。

剧本分两类：
- **里程碑剧本**：用于验收（"M1 完成" = M1 剧本两端一致）
- **机制剧本**：走动 / 对话 / 旁白 / 选择 / 答题 / 宝箱 / 商店 / 战斗 各一条，用于定位

"自动播放 / demo 模式"是这套机制的免费副产品：挑一条剧本循环跑即可。

进度跳转走**存档式**：`Recorder.save()` 存的 9 组信息就是原作者对"进度"的
完整定义，直接复用其建模；而 web 版本来就要做存档，跳转是它的副产品。

## 6. 让失败大声

本项目最贵的坑全都是"失败长得和成功一样"。已知实例：

| 现象 | 为什么没人发现 |
|---|---|
| 3 行 Fight 数据用 Windows 反斜杠 → macOS 上战斗背景全白 | `ImageIcon` 路径错了不抛异常、不返回 null，只给宽度 −1 的空壳 |
| 27 帧 NPC 素材从未交付，三个 NPC 一直隐形 | 同上 |
| 3 处装备图标错别字（颀鉴/颀崟、钛珖/钛銧、银项链/银项练） | 同上 |
| 取景器截了 4800 帧战斗，90% 是静止废帧 | "文件写出来了"被当成"画对了" |
| `awk '/^Fight$/'` 匹配不到任何东西 | 文件是 CRLF，`$` 匹配不上 `Fight\r`，而"没找到"就是它的通过条件 |

因此 **数据烘焙管道必须对每条资源路径做 stat 硬校验，缺失即构建失败**。
`readImage` 已加去重警告（commit `fix(diag):`），一次全量扫描立刻扫出 31 个缺失路径。

**工具能重新生成产物，产物不能反过来生成工具** —— 这是 `tools/` 比
`tools/reference/` 更重要的原因，也是战斗序列只入库 1/5 采样的理由
（全量 4800 帧 WebP 为 335MB，而 git 历史删不掉）。

## 8. 对已改动的原版代码的说明

迁移期内 Java 源码必须**可运行**才配当规格，因此做了三类修改，每类一个
独立 commit，均不触碰游戏逻辑：

- `fix(io):` 4 个 I/O 点显式 GBK（6 行）
- `fix(path):` `tools.Reader.normalizePath` 跨平台路径规范化
- `fix(diag):` `readImage` 缺失警告（只加诊断，不改行为）
- `feat(clock):` `tools.Clock` 时间缩放（`factor=1.0` 时恒等）

**脚本数据一行未改。** 那 3 行反斜杠路径是 web 数据烘焙管道的现成测试用例 ——
"修好"它们会让路径规范化逻辑永远测不到。
