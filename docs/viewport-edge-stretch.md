# 地图边缘的那 0.8% 横向拉伸：裁定与复刻

xl-9bd.7 的验收标准之一是"裁定原版在地图边缘是否存在约 0.8% 的横向拉伸（这是
推算、未经测量），并记录是否复刻该行为"。

**裁定：存在。横向 0.787%、纵向 1.266%。而且不止在地图边缘 —— 一屏装得下的
静止地图（32×20）是每一帧都被拉伸的。Web 侧复刻了它。**

## 算术

两处原版代码合起来产生这个效果。

`src/scene/OtherEvent.java:90-99`（`calOffset`，单位是 8 px）：

```java
firstTileX = (int) Math.floor(-offsetX / 8);
lastTileX  = firstTileX + (int) Math.floor(ScenePanel.WIDTH / 8) + 1;  // +129
lastTileX  = Math.min(lastTileX, map.getCol() * 4);                    // 夹取
```

`src/scene/Map.java:45-50`（`drawMap`）：

```java
g.drawImage(image, 0, 0, 32 * 32, 20 * 32,                 // 目标：整块 1024×640
            firstTileX * 8, firstTileY * 8,
            lastTileX * 8 - 8, lastTileY * 8 - 8, scene);   // 源：注意那两个 -8
```

源矩形的宽是 `(lastTileX - firstTileX - 1) * 8`。没被夹住时 `lastTileX =
firstTileX + 129`，宽正好 `128 * 8 = 1024`，缩放系数是 1。**被夹住时少一格**：
宽 1016，铺进 1024 的目标矩形，横向放大 `1024 / 1016 = 1.00787`；纵向同理
`640 / 632 = 1.01266`。

主角与 NPC 不走这条路：`Role.drawHero(g, offsetX, offsetY)` 只是平移。所以被
夹住的帧里，**地形被拉伸而人物没有**，两者最多错开 8 px（在地图最右/最下沿）。

另有一条相关的发现：`Map.isStatic` **永远是 false**。字段的 Java 默认值是
false，而构造函数里唯一一处赋值也是 `isStatic = false`（`row > 20 || col > 32`
时）。于是 `drawMap` 里那条 `else` 分支（`g.drawImage(image, 0, 0, scene)`，
不缩放）是死代码，**所有地图都走缩放这一条**。静止地图之所以看着正常，是因为
误差只有 0.8%，不是因为它走了另一条路。

## 证据

拉伸本身是**实测**的：三份 trace 逐 tick 的 `viewport` 六元组算出的源矩形是

| trace | 场景 | 瓦片 | tick 数 | 源矩形（去重） |
|---|---|---|---|---|
| bigmap-walk | 大地图 | 100×80 | 842 | 1024×640 |
| dorm-intro | 脚本1 | 32×20 | 4123 | 1016×632 |
| dorm-walk | 宿舍 | 32×20 | 538 | 1016×632 |

也就是说，两份 32×20 的剧本、合计 4661 个 tick，**每一帧**都落在被夹住的那条
分支上，源矩形是 1016×632。夹取分支不是推测出来的，它在真值里被原版执行了
4661 次。

卷动地图上"走到最右边也会夹住"这一条**是推算，不是实测**：`bigmap-walk` 这份
剧本没有走到那一段（它的源矩形恒为 1024×640）。推算的依据是同一段代码的同一个
`Math.min`，以及地图数据本身 —— 100×80 的地图里，位于"镜头已被右侧夹死"那条
带子（瓦片 x ≥ 84）内的可走格有 508 个，被下侧夹死那条带子（y ≥ 60）里有 475
个。**这 508/475 个格子与主角出生点是否连通，没有验证过。**

## 复刻与否

**复刻。** `web/src/scene/viewport.ts` 的 `mapTiles()` 把 `calOffset` 的六元组
翻译成地图底图这一帧该怎么贴，`sceneRenderer` 每帧套用；主角仍然只按
`offsetX/offsetY` 平移，与原版一致 —— 连"地形与人物错开"这个瑕疵一起复刻。

理由：不复刻的代价不是"少一个 bug"，而是**每一帧的地图都比原版矮一点窄一点**
（32×20 的场景是每一帧，卷动场景是边缘帧）。跨端逐帧像素比对（xl-9bd.8）以
原版为准，那样它永远收敛不了，而"差 0.8%"在肉眼下只表现为一点点糊，查不出来。

## 怎么复刻：分段 1:1 平移，不是一次缩放（xl-9bd.16）

最初的复刻是给地图精灵一个 `scale.set(1.0079, 1.0127)`。**那样只把偏离从 83%
降到 38.5%，而且剩下的偏离铺满全屏**：按 64×64 分格统计，160 个格子全部有偏
离、每格 28–59%。两条原因，都量过：

1. **过滤方式。** Java2D 的 `RenderingHints.KEY_INTERPOLATION` 默认最近邻，
   Pixi 的 `TextureSource` 默认线性过滤。改成最近邻后第 0 帧从 38.51% 掉到
   1.02%。
2. **采样点由谁算。** 交给 GPU 的 UV 插值就等于把"每个目标像素取哪个源像素"
   交给了一个精度拿不准的东西。实测（dorm-walk 第 0 帧，最近邻）：横向 1024
   列全对，纵向却有 10 整行取到了上面一个像素 —— 误差呈 `-5.24e-5 × y` 的相对
   形状，y 接近 640 时约 0.03 px，而这个映射相邻两点的最小间距只有
   1/160 = 0.00625 px。**误差与判定间距同量级，加偏置修不好**：往上补够 0.03
   就会把另一端间距 0.00625 的点顶过界。

所以换一种表述。原版的采样公式是（**实测**：把一张 1024×640 的图按
`drawImage(img, 0,0,1024,640, 0,0,1016,632, null)` 缩放后逐像素读回，1024 列与
640 行全部符合；按 `floor(i * 源 / 目标)` 截断则有 504 列、312 行对不上）：

```
源像素 = floor((目标像素 + 0.5) * 源边长 / 目标边长)
```

这个函数每一步要么加 1、要么原地不动，于是把"源下标 − 目标下标"相同的目标像素
归成一段，**每一段就是一次 1:1、整数对齐的平移**。1016→1024 分 9 段、
632→640 分 9 段，横竖相乘 81 块；没夹住的帧退化成 1 块。每块按 1:1 贴，目标
像素中心落在源像素正中，离判定边界有 0.5 px 的余量 —— 比上面那 0.03 px 大一个
多数量级，于是这件事不再依赖采样器的精度。段界全程用整数算，跟机器无关。

**结果**：`tools/compare-frames.sh dorm-walk` 第 0 帧从 38.51% 降到 0.3317%，
有偏离的格子从 160/160 降到 5/160。更直接的判据是把"原版这一处画的仍是地图
底图"的像素挑出来单独比：652306 个这样的像素，Web 侧**一个都没取错**。剩下的
0.33% 全部落在 2 个 NPC、宝箱、以及走到萧逸才跟前那个对话框的格子里。

对应的可执行断言在 `web/src/scene/viewport.test.ts`：一条钉住分段（"夹住的帧
地图被切成多块，没夹住的帧只有一块 1:1"），一条把 81 块逐像素展开、与上面那条
采样公式对齐（"碎片展开后逐像素等于原版的最近邻采样公式"，分母 655360）。
